# 后台需求与复用拆分

日期：2026-09-21。依据：[需求基线](../../docs/requirements/baseline.md)、[原 PDF 覆盖核对](../../docs/requirements/pdf-coverage.md)。本次沿用已逐页复核的文档，未重新取得或复核 PDF 原件。

下表“需求”来自原文；优先级、工程拆分和验收是实施建议。所有后台真实服务当前均未实现。R0–R5 对应 [交付计划](delivery-plan.md) 中的迭代顺序，不是原文的三阶段名称。

## 1. 岗位、地区与身份

- 全国管理员：统一标准、全局配置、跨区授权、终审及全国发布；是否可看原稿和身份字段由具体权限决定。
- 省级/区县运营：授权区域内用户、稿件、内容、活动、数据。原文市级评审节点不代表已有市级管理员授权规则。
- 内容运营、评审管理、数据运营：是岗位，可以与区域范围组合，不为每种组合另建一套账号系统。
- 专家：仅访问分配且仍有效的任务；盲审稿件另设脱敏投影，不能只隐藏页面字段。
- 投稿用户：独立用户身份和微信绑定；后台员工账号与投稿人资料区分，通过受控绑定关系支持同一人兼任专家。

建议拆分 `User/Member`、`StaffRole`、`Organization`、`Region`、`Membership/Scope`。复用底座 RBAC 与认证机制，补业务授权和 C 端会话适配；客户端传入的 `regionCode`、`tenantId` 不作为访问授权依据。

## 3. 首个业务闭环

用户登录 → 保存云草稿 → 附件上传完成并通过可用性检查 → 确认协议版本 → 正式提交并冻结版本 → 后台按地区查看 → 初审通过/退修 → 用户见进度、按原业务编号提交新版本。

这一闭环先落地 B-01/B-02/B-11 与部分 B-05。下一轮接专家任务、量表、结果审批、公示，再扩活动/典籍。不能将一次“通过”同时解释为初审通过、获奖、公开和入藏。

建议最小实体及其职责：

| 领域 | 实体                                                               | 必须保留的关系/约束                                                        |
| ---- | ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 投稿 | Submission、SubmissionRevision、Attachment、AgreementRecord        | 业务编号稳定；每次提交冻结新版本；附件与协议记录归属到人和版本             |
| 评审 | ReviewDefinition、ReviewStage、ReviewTask、Rubric、Score、Decision | 任务绑定流程/量表/稿件版本；任务归属和有效期可校验；决定不能由前端状态覆盖 |
| 发布 | Publication、Certificate、Notification、OutboxEvent                | 结果批准与公开分离；公示字段白名单；签发/撤回与消息重试可追溯              |
| 内容 | Article、ContentTranslation、Collection、Volume、Chapter           | 内容语言版本各自审核/上下架，典藏引用已授权版本                            |
| 活动 | Venue、Activity、Registration、Attendance                          | 名额原子更新；本人及运营的取消/签到权限不同                                |
| 治理 | AuditEvent、FileAsset、RegionRoute、MetricDefinition               | 审计不依赖页面；文件下载和异步作业延续原始授权范围                         |
