# 整合方式与敏捷交付计划

日期：2026-09-21。以下目录、接口与工作包为实施方案，未创建对应运行服务。采用决策见 [选型](selection.md)，需求追溯见 [需求拆分](requirements.md)。

**后台专项阶段记录：界面先行。** 用户明确暂不考虑真实数据加载和存储，已先完成`apps/admin`的13页/11类业务界面及内存交互（5174），实际范围见 [后台演示说明](../../docs/frontend/admin-demo.md)。这是独立的UI工作包，不表示下方R0后端PoC或BK真实接口任务完成；Java、数据库、鉴权、工作流和HTTP接入仍待开发。

## 1. 一个底座，分清业务模块

```text
现有 Uni-app 用户端（H5 开发预览 5173）
    ↓ 异步业务服务 + uni.request 适配
平台业务 API（建议统一 /api/v1；正式以修订后的 OpenAPI 为准）
    ↓
Spring Boot 模块化应用
    ├─ 上游：账号/角色/菜单/组织/字典/文件/审计/调度/WarmFlow
    ├─ 家风：会员与区域授权/投稿版本/评审评分/内容发布/活动
    ├─ MySQL + 与上游兼容的 Redis + 对象存储适配
    └─ 作业与服务接口 → 后续私有 OCR / 知识库 / 文档导出

配套 plus-ui Vue 管理站 → 同一后端的后台接口
```

建议工程落点：

| 位置                                 | 责任与复用方式                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `apps/miniapp`（已存在）             | 保留用户端页面、Uni-app/Wot UI 和纯领域校验；新增异步 service/adapter，按闭环逐页接入                                     |
| `apps/admin`（计划）                 | 从锁定的配套 Vue 管理端引入；复用布局、路由权限、表格、上传、字典、任务页面；家风页面置于独立 `views/jiafeng` 与 API 目录 |
| `apps/server`（计划）                | 保留若依多模块结构与依赖管理；增设 `ruoyi-modules/ruoyi-jiafeng` 业务模块，不将业务状态散放到框架 system 模块             |
| `contracts/openapi.yaml`（已有草案） | 唯一对接契约，先修订再生成/实现客户端；框架原生管理 API 与面向小程序的业务 API 分开标注                                   |
| `deploy`（计划）                     | 环境示例、迁移、服务编排、存储配置、备份恢复手册；先最少进程，按实际依赖补调度/监控                                       |
| `projects/backend`（本轮建立）       | 需求、决策、迭代与候选证据，不放运行密钥                                                                                  |

管理端默认开发端口可能与现有 5173 冲突。接入时为管理端另配 **5174（建议，尚未启动）**，后端端口按上游配置核验后记录；不将建议端口写成已部署地址。

上游系统通知不等于完整用户消息中心；部门数据权限不等于行政地区/机构授权；CRUD 生成器只生成结构，状态流转、发布和评分仍需领域服务。复用已有权限框架和流程引擎，避免为家风再造通用系统。

## 2. 先修正前后端契约

当前 [OpenAPI 0.1.0 草案](../../contracts/openapi.yaml) 尚无 HTTP 实现；[useDemo](../../apps/miniapp/src/composables/useDemo.ts) 和 [领域类型](../../apps/miniapp/src/domain/types.ts) 已增加更多演示能力。

| 当前差距                                                                        | 首轮修订方向                                                                                              | 接入验收                                                               |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 路线文档使用 `/api/v1/submissions`，OpenAPI 使用 `/v1/works`；评审/AI命名也不同 | R0形成一个版本的路径清单，区分私有稿件与公开作品；以更新后的OpenAPI为准，不维护两套文档接口               | 服务、管理端、小程序使用同一契约版本                                   |
| `RegionId` 仅4种；前端已覆盖34省与海外                                          | 地区目录/编码与筛选范围分开；`all` 不可作为真实投稿归属；海外地点有独立字段                               | 区域筛选不扩大授权；归属非法被拒绝                                     |
| 草稿无Delta、多主题、海外、附件、修订来源                                       | 明确白名单富文本结构、plain text、主题数量、附件ID、稿件版本、作者与投稿人、字段长度                      | 编辑后重读一致；服务端也验证内容及附件归属                             |
| 本地退修覆盖Work正文，保留的只是版本号与评语                                    | Submission下建立不可变Revision；流程任务和意见指向对应revisionId                                          | 退修后仍能读取旧正文及其评语                                           |
| 当前状态混合审核、入围、获奖、入藏                                              | 分离处理状态、评审决定、公开状态；展示文案由适配层计算                                                    | 初审通过不会自动公示/获奖；撤回发布不抹去评审历史                      |
| 缺登录、授权上下文、文件上传、协议证据                                          | C端会话与后台认证边界；上传意图/完成/处理状态/授权下载；协议版本及确认记录                                | 失效会话、跨人文件、扫描未完成、过期协议有明确结果                     |
| 公开与私有作品混在列表模型                                                      | 列表摘要与详情分离；公开DTO、本人DTO、专家匿名DTO按白名单构造                                             | 公开响应、文件名、导出及附件元信息不泄露盲审身份                       |
| 评分、公示、消息、证书、资讯缺完整契约                                          | R1补资讯管理/公开读取/发布/下架；R2补任务详情、量表、评分草稿/提交、决定、公示/撤回和消息；R3按规则接证书 | 资讯公开读取与下架一致；同任务并发提交只接受有效一次；只能发布批准版本 |
| 同步computed仓库与`safely`无法处理异步                                          | 新增Promise业务接口、异步mock与http适配；通过`uni.request`隔离跨端请求和框架响应                          | loading/empty/error/success、会话失效、旧请求覆盖新请求、重试都可验证  |

保留草案已有的 `Idempotency-Key`、`ETag/If-Match`、稳定错误码、requestId、不可见返回404等设计。ID使用字符串，时间采用带时区格式；创建请求不接受客户端指定归属人、最终分数、正式状态或数据源。

现有本机存储仍用于演示模式，不能将 `DEMO-` 编号、`isDemo:true`、模拟证书/评分自动迁入真实库。HTTP 模式的业务操作失败时应明确报错，不静默回落到 Mock 产生“成功”。

| 轮次                | 可展示增量                                                  | 复用内容                                  | 完成条件与依赖                                                                                                         |
| ------------------- | ----------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| R0 底座验证         | 管理站登录、角色授权、文件上传与一条样例审批可运行          | 锁定后端与Vue前端、系统/文件/WarmFlow模块 | clean checkout可构建启动；许可/SQL可用；岗位权限、文件私有下载、流程退回/会签/版本验证；完成正式契约方案；当前尚未执行 |

| R2 专家评审与结果   | 分配任务、匿名评分、人工决定、公示、通知、真实投稿/评审统计 | WarmFlow、任务调度、图表及通知基础        | 已确认试点规则；每次评分绑定量表/稿件/流程版本；越权、任务过期、回避、重复决定、公示撤回及对账通过                     |

## 5. 后续维护与扩展约束

1. 每个上游单独记录仓库、完整commit/tag、依赖锁、原始许可证、SQL/素材/插件来源及修改目录。实际导入时更新根 `source-lock.json` 和 `THIRD_PARTY_NOTICES.md`；调查清单不冒充安装清单。
2. 保持上游模块结构，将家风业务置于独立模块；保留可追溯的upstream基线或vendor导入提交。框架升级另开分支，通过登录、权限、文件、流程、投稿闭环后合并。
3. 工作流引擎只编排任务。专家评分、回避、匿名、作品版本、授权、公示决定由家风领域服务控制；不为省份复制34套工程。
4. 在部署扩省前实现可信区域路由、独立库/凭据与附件/缓存/检索/备份隔离。全国公开副本采用批准字段；同步用outbox与幂等消费，验证重试、撤回、删除传播和对账。
5. AI、电子签署、视频等通过受控适配器和作业状态接入。许可、费用与外网边界随实际组件逐项记录；不将外部SDK或服务密钥下放页面。
6. 每轮同步需求变更、OpenAPI、演示状态和实际验证。按仓库要求运行`typecheck`、`test`、`build:h5`、`build:mp-weixin`；界面变化补桌面/手机与受影响小程序交互验证。
