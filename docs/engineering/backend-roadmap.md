# 后续后端开发路线与接口边界

编制日期：2026-09-20。本文是从《小程序制做要求.pdf》提炼的实施建议，**不表示后端已实现或已部署**。当前目标是前端展示与沟通；原文全国规模、真实 AI、物理分库等是后续产品要求，不是本次演示的验收结论。

**2026-09-21 更新：** 最新工作为后台立项与开源整合方案，进入开发时使用 [后台项目](../../projects/backend/README.md) 的最新需求、选型和R0–R5计划。下文为早期设计输入，路径、阶段及AI候选尚未实现；[契约修订清单](../../projects/backend/delivery-plan.md) 已指出本页与OpenAPI的路径/模型差异，必须统一后再编码。

## 1. 先建立业务边界，随后替换模拟数据

建议以 Spring Boot 模块化应用启动，AI/OCR 独立进程。优先验证 RuoYi-Vue-Plus 基础模块，或在流程/商城优先时核清资料条件与兼容性后整体改选芋道；决策理由和许可见 [最新选型](../../projects/backend/selection.md)。本项目尚未执行后台运行验证，仅当实际吞吐、团队边界或独立发布需要时拆分更多服务。

| 领域       | 第一批实体                                            | 首次真实接入范围                                       | 以后扩展                                            |
| ---------- | ----------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| 身份与地区 | User、Role、Organization、Region、RegionMembership    | 微信登录会话、用户资料、地区授权、后台账号             | 实名核验供应方、专家资质、回避关系、多因素认证      |
| 投稿       | Submission、Revision、Attachment、ConsentRecord       | 草稿保存、八大体裁、版权勾选记录、上传、提交、我的作品 | 在线线下统一导入、Word/PDF 解析、重复检测、电子签章 |
| 评审       | ReviewDefinition、Stage、Task、Score、Decision、Event | 一条经确认的审核流程、退回修改、进度时间线             | 六级可配置、盲审、会签、评分规则、超时、异议        |
| 内容与典籍 | Article、Work、Collection、Volume、Chapter            | 内容列表/详情、标签、典藏阅读、收藏                    | 专家编纂、竖排排版、双语内容版本、出版导出          |
| 活动与阵地 | Venue、Activity、Registration、Attendance             | 活动信息、预约、名额与取消                             | 地图、签到、课程台账、结业证书                      |
| 消息与证书 | Notification、Certificate、Publication                | 站内消息、已通过作品公开展示                           | 微信订阅消息、模板证书、下载与验真                  |
| AI 与资源  | AiJob、AiAudit、KnowledgeSource、FileAsset            | 接口占位和任务状态，随后接私有 OCR/问答                | 私有生成/朗读、合规检查、知识库迭代、资源清理       |
| 文创与公益 | Product、Order、Claim、Quota                          | 第二阶段以后，先确立公益/商业两套流程                  | 库存、支付退款、发票、政务定制与履约                |

原文“六大核心表”宜理解为六类核心领域，不能只用六张大表容纳所有历史、权限、附件、评分与日志。领域对象分别拥有状态、创建/更新时间、版本与归属地区；身份证等敏感信息另设最小访问边界，不塞进所有返回 DTO。

## 2. 前端应遵守的接口约定

接口路径为建议草案；实现时以正式 OpenAPI 为准。前端页面只调用业务 service，不直接拼接存储键或依赖某个后台框架分页字段。

| 行为          | 建议接口                                                                | 后端必须保证                                                  |
| ------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------- |
| 登录          | `POST /api/v1/auth/wechat/session`                                      | 服务端交换 code，返回平台会话；微信登录不能等同法定实名       |
| 全国/地区首页 | `GET /api/v1/home?regionCode=…`                                         | 仅返回允许公开的地区内容，不按请求参数直接扩大权限            |
| 保存/更新草稿 | `POST /api/v1/submissions`、`PATCH /api/v1/submissions/{id}`            | 所有权检查、字段校验、版本冲突返回                            |
| 上传附件      | `POST /api/v1/files/upload-intents`、`POST /api/v1/files/{id}/complete` | 限制类型/大小、短期授权、病毒/内容处理状态、归属绑定          |
| 正式提交      | `POST /api/v1/submissions/{id}/submit`                                  | 幂等键、协议版本与确认时间、冻结稿件版本、创建评审实例        |
| 我的投稿/进度 | `GET /api/v1/me/submissions`、`GET /api/v1/submissions/{id}/timeline`   | 当前人权限、可见评语脱敏；不存在与越权不泄露细节              |
| 专家评分      | `POST /api/v1/review-tasks/{id}/scores`                                 | 任务归属、阶段/截止校验、评分范围、匿名字段、并发提交         |
| 典籍阅读/收藏 | `GET /api/v1/collections/{id}`、`PUT /api/v1/me/favorites/{id}`         | 发布版本、资源权限、收藏幂等                                  |
| 活动报名      | `POST /api/v1/activities/{id}/registrations`                            | 截止时间、名额原子扣减、重复报名、取消规则                    |
| AI 作业       | `POST /api/v1/ai/jobs`、`GET /api/v1/ai/jobs/{id}`                      | 配额、输入输出审查、来源、超时/取消、审计；前端不持有模型密钥 |

统一约定：ID 用字符串避免 JavaScript 大整数精度丢失；时间用带时区的 ISO 8601；分页明确 `items/nextCursor` 或 `items/total`；错误包括稳定业务 code 与 requestId；用户语言与地区分离。服务端从认证会话和授权关系解析租户，不能信任前端提交的 tenantId。任何 mock 状态的“通过/获奖”都不能迁移为真实生产评审记录。

## 3. 投稿与评审状态机

建议稿件外部状态：`DRAFT → SUBMITTED → IN_REVIEW → SELECTED / REJECTED`，退修使用 `REVISION_REQUIRED`；公示、典藏作为后续独立发布状态，不与评审结论混用。具体名称在 API 评审时确定。

- 每次提交冻结内容 revisionId，评审意见必须引用该版本；退回修改产生新版本，不能覆盖专家已评内容。
- 六级名称和节点目前在原文标记“需讨论确定”，先建可配置流程定义，不将六级写死在数据库列名中。演示可以显示原文建议节点，真实系统须业务确认。
- 引擎负责任务流转；评分量表、专家冲突、回避、匿名视图、判定阈值、名单与证书由业务领域负责。
- 重试、会签、补充专家、撤回和跨级复核都要有审计事件；展示时间线从事件投影生成，不能单凭第几个步骤推断业务结果。
- 真实公示需要有发布动作、授权范围、发布时间和撤回记录；AI 评分只作为参考，不自动变成最终评审决议。

Flowable 的 Java 引擎与 Spring 集成可用于任务编排；RuoYi-Vue-Plus 当前已经采用 WarmFlow。建议各自完成一次相同的复杂流程验证再选择，避免同时部署两个引擎。[Flowable 官方仓库](https://github.com/flowable/flowable-engine)、[RuoYi-Vue-Plus 官方仓库](https://github.com/dromara/RuoYi-Vue-Plus)。

## 4. 省级物理隔离：从第一张表开始预留，逐步建设

原文要求全国总库与省级分库物理隔离。最终“独立数据库”“独立实例/集群”还是“独立基础设施”的验收边界需确认。推荐按省规划独立数据库与凭据，涉及强隔离时按省独立实例/集群、网络与密钥；同一 MySQL 实例中不同 schema 不能未经约定就称为满足所有物理隔离要求。

推荐控制面与数据面分开：

1. 全国控制面保存地区目录、路由、统一标准、必要身份索引和汇总口径；避免复制全部省级敏感数据。
2. 省级数据面保存投稿、附件、评审、活动和本省权限关系。查询通过服务端授权后的省级路由选择，默认拒绝未授权地区。
3. 全国典藏与公示采用明确授权的发布副本；全国统计使用聚合事件或脱敏数据管道。原文“所有数据可同步总库”须进一步明确数据范围、合法授权、延迟、撤回和冲突规则，不能默认无限复制隐私。
4. 跨库写入采用 outbox/事件、幂等消费、重试和对账；早期避免分布式大事务与运行时跨省 join。事件记录来源省份、实体 ID、版本、事件 ID 与发布时间。
5. Redis 的 key/队列、Elasticsearch 索引、对象存储访问策略、备份、导出文件、AI 向量库和审计日志都要纳入同一隔离模型。数据库分开但搜索或缓存串数据仍然不合格。
6. 先用两个测试省份验证越权、错路由、恢复、同步和删除；验证通过后按基础设施模板扩展。租户过滤/动态数据源只能构成其中一部分。

MVP 允许先部署一个试点省份，但要在数据契约中明确 `regionCode` 与内部租户归属，不把演示切换地区当作物理分库实现。具体基础设施尚未配置。

## 5. 私有 AI 与资源处理

原文明确 AI 数据不出服务器、不调用外网通用大模型。实施时需选择可私有部署且许可允许的模型与权重，独立验证 GPU/CPU、吞吐和成本；“部署 Dify/FastGPT”并不自动满足这一要求。

处理链建议：上传隔离区 → 文件扫描/解析 → OCR → 用户校对 → 入库 → 授权检索 → 私有模型 → 输出审查 → 人工确认/发布。检索必须在召回前落实权限过滤，审计保存 prompt 版本、模型版本、授权来源、结果处理与 requestId，日志对敏感信息脱敏并设置留存策略。

首批只做投稿帮助问答、可追溯典籍问答和 OCR；诗词格律、图文转视频、方言配音、个性化推荐均单独评测。古籍和手稿 OCR 用真实样本统计错误率，提供校正入口。[PaddleOCR 官方仓库](https://github.com/PaddlePaddle/PaddleOCR)。

Dify 多 workspace 与 FastGPT 类 SaaS 的许可边界不相同，实施前按具体运营模式核对，并保留版本许可快照。[Dify LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)、[FastGPT LICENSE](https://github.com/labring/FastGPT/blob/main/LICENSE)。

## 6. 敏捷阶段与完成条件

以下是工作包顺序，不是未经估算的工期承诺。每次迭代都应保留可运行演示，反馈同步更新需求、界面与接口。

| 迭代              | 可展示/可用结果                                               | 完成条件                                                                       |
| ----------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 0：当前前端       | 地区浏览、投稿草稿/校验、进度、典藏、活动、个人中心及扩展入口 | 明确演示数据；交互可运行；构建通过；不假装已接微信、支付、AI                   |
| 1：真实内容与投稿 | 后台账号、内容发布、登录、草稿、附件、投稿列表                | 一条从投稿到后台处理的真实链路；权限、上传归属和重复提交测试；数据库迁移可复现 |
| 2：评审闭环       | 确认的评审流程、专家评分、退修、公示                          | 对角色与区域越权、并发评分、版本冻结、异常恢复完成验收；流程变更有版本         |
| 3：活动与典藏     | 活动报名、签到、证书、分卷阅读与收藏                          | 报名并发与名额、取消、证书授权、发布与撤回验证                                 |
| 4：AI 与多省试点  | 私有 OCR/问答、两省隔离、全国汇总                             | 真实样本质量指标、离线链路、授权检索、跨省越权、同步重试与恢复演练             |
| 5：商城与规模化   | 商业交易/公益申领、VR/视频、更多省份                          | 支付回调与对账、库存、域名/素材、真机性能和容量测试分别完成                    |

## 7. 需要在后端正式开发前确认的事项

- 六级评审的真实层级、谁有终审权、评分规则、回避/申诉/退修与公示期限。
- “实名认证”的目标、验证对象、是否涉及未成年人、可用微信/机构资质及现成服务供应方。
- 省级独立存储的具体隔离等级、全国同步范围、身份跨省使用和管理权限。
- 原文百万日活、1 万在线、峰值 10 万并发的统计口径、同时发生的行为、目标终端与预算；不能把在线人数当作接口 QPS。首屏 1.5 秒也需规定网络、设备、缓存与素材条件。
- 微信基础库 2.10.0 与所选 Uni-app/组件版本的兼容矩阵，目标 iOS/Android、平板、弱网和老年模式要求。
- 英文及其他语言的首批范围、翻译来源，AI/视频/支付/直播服务资源和许可。

以上问题不阻碍当前界面演示，但决定生产系统设计和验收。原文指标、法规与平台规则需在真实上线阶段按当时官方要求复核，不能由模板仓库的说明代替。
